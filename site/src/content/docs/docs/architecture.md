```
src/
  Griff                    Engine core: scenes, serialization, editing/undo, runtime, physics,
                           render lists, audio (mixer, sound and music synths), networking
                           (UDP with reliable and unreliable messages, and multiplayer on top),
                           projects and templates, tables of game data (Data). No UI dependencies.
    Modules/               The genres, each in a folder of its own: Battles, BlockWorlds, Cards, Contraptions,
                           Dungeons, FallingBlocks, FirstPerson, Match3, Puzzles, Strategy, Tactics
  Griff.Scripting          Roslyn script compiler, hot reload, game exporter
  Griff.Graphics           How a frame is drawn, apart from any graphics API: IRenderer, the DrawList every renderer
                           draws (quads in clip space and the passes that draw them) and the shaders
  Griff.Graphics.OpenGL    The desktop's renderer: the draw list with OpenGL 3.3
  Griff.Fonts              Fonts read and glyphs rasterized in plain .NET (StbTrueTypeSharp), packed into atlas
                           pages and laid out as a quad a glyph; a font name resolved in one place (FontCatalog:
                           BuiltInFonts with their licenses, a project's font files, installed fonts)
  Griff.Platform.Windows   WGL context, WPF game surface, frame pacing, input, sound output and decoding
  Griff.Editor             WPF editor: modules, commands, panels, design system (Themes/)
  Griff.Player             Runs exported games
  Griff.Web                Runs games in a browser: .NET for WebAssembly, the draw list drawn with WebGL 2 (a proof so far)
tests/
  Griff.Tests              Unit and integration tests, including playing every template
  Griff.Editor.Tests       The editor's real services, the agent surface, and exported games run for real
site/                      griff.games: an Astro Starlight site, deployed to GitHub Pages (see site/README.md)
```

The engine lives in `Griff` so that the editor, the player and the tests all use one model. Its layers: `Griff.Scenes` is the data (entities, components and how they're saved), `Griff.Runtime` runs it and `Griff.Rendering` turns it into draw lists. What both sides need lives below them, in `Griff` (`Color`, `Box`, `Ease`, `Rand`), `Griff.Input` (`Key`) and `Griff.Data` (tables: `Table`, its columns and cells, `Dice`, their files, CSV, formulas (`Formula`, read into a small tree and worked out by `TableEvaluation`, with powers and logarithms of its own in `FormulaMath` so every machine gets the same bits), the `Curve`s level columns are generated from, and the `TableSet` a game reads, its formulas worked out; a table never changes, so a running game, the editor and an undo history each hold one safely, and every edit makes a new one; and balance simulations: a `Simulation` (its `.sim` file, `SimulationFile`) played by `SimulationRunner`, each run a headless `Game` of the arena scene (or a `SimulationScript`) with a seed of its own from the simulation's, the step, the rows' names and the run's number, in blocks of runs shared across the `Workers` and added up in block order, so any number of cores gives the same `SimulationResults`); an entity knows whether it's active (`IsActive`, counting its parents) and which machine runs it in a network game, and a component that needs the running game gets a small `IGameContext` rather than the `Game`.

A game moves in fixed steps (`Time.StepRate`, 60 a second): each frame the screen shows, `Game.Advance` takes as many as the real time since the last frame holds (none on a fast screen's frame, two on a slow one's; at most a tenth of a second's worth, so a stall slows the game rather than piling up steps), keeps the rest for the next frame, and says how far the frame is between the last two steps (`Time.Blend`). A frame within 12% of a whole number of steps counts as exactly that many, so a steady screen takes the same steps every frame instead of now and then none and then two, and the player times frames by the compositor's vertical blank (`FramePacer`, from `DwmGetCompositionTimingInfo`), the screen's steady beat, rather than when the UI thread got to them. Input counts in the next step taken, once: each step ends the input's frame, and a frame with no step keeps what was pressed for the next. While the renderer builds a running game's frame, each transform's `WorldMatrix` is where it's drawn: one that moved in the last step is placed between where it was as the step began (each transform remembers that the first time it moves in a step) and where it is, inside wherever its parent is drawn, so children, the camera and everything pinned to it glide together. What jumped in the step is drawn where it is: added to the scene, moved to another parent, `Teleport`ed (respawns and doors do), a camera snapping to its target, a move further than a quarter of the view, a turn of more than 90 degrees or a flip; so is everything on the step a scene came in on, and a game held still (`Game.ShowAsIs`, which the editor's pause and rewind use). What's drawn from a component's own state rather than a transform goes between steps the same way, by the same rules (`StepBlend`, from `Drawing.Blend` or `FrameDrawing.Blend`): a `Smoothed<T>` value remembers what it was the first time it changes in a step, as a transform does, and is drawn between that and what it is only if it changed in the last step and its entity (or one it's inside) didn't jump. Particles and rain keep where each was before it last moved (and how it was turned and how far through its flutter or flicker), a trail's copies how old they were, a sprite's, text's or tilemap's tint, a sprite's flash and a sprite's and text's size are `Smoothed`, as are the screen's fade and flash, the camera's zoom, shake, background and turn, the screen effects' settings, a light's reach, color, brightness and flicker, the ambient light of a room fading in, a bar's value and trail, health (for the meters that show it), a beat pulse settling back (a beat landing is drawn as it is), a crumbling platform's shake, and a first-person viewer's look up and down and walk's bob, its weapon's kick, flash and coming up, and billboards bobbing; debug shapes a step draws are drawn between those of the step before when they're the same shapes in the same order. A match-3 board's slides, falls and clears each keep how far along they were as the step began, and the gems that came home or cleared away in the step are drawn the rest of the way; a falling-block board's piece is drawn between where it was and is when it slid or fell (as it is when it comes in or turns), full rows shrink between steps, and the step they go in they shrink the rest of the way as the rows above drop into their place. Strategy and tactics meters, building and training progress, order markers and notices, and a block world's digging are drawn between steps too, and every system HUD is pinned to the view as it's drawn. What changes all at once (a board's tiles, a sprite's frame, a turned piece) is drawn as it is. Ropes and wires follow the transforms they join. The step rate is the project's (`Project.StepRate`, in `project.griff`), which every host sets as it starts a game (`game.UseProjectSettings(project)`, with the controls). `FixedStepTests` plays the same input at 30, 60 and 144 frames a second and with frames all over the place, slow motion and hit stop in it, and gets the same game to the last bit; and a host and a player on screens of different rates stay in step. Each step goes through the game's frame: a list of steps in eight phases (begin, logic, scripts, simulate, physics, resolve, present, end), taken in order (`Game.Tick` takes one step by hand, of any length); `Game.Frame` lists them, and `FrameTests` pins the order, so changing it is always on purpose. The steps belong to systems: Griff's keep what a kind of game tracks while a scene runs (levels' doors and conversations, switches, dragging, panels, and each module's: battles, block worlds, cards, contraptions, dungeons, falling and match boards, first person, puzzles, strategy, tactics) and forget it when the scene changes, and scripts add their own. The scene keeps its components by type as it changes (`Scene.All<T>()`, `Scene.Active<T>()`, in hierarchy order, and safe to go through while spawning and destroying), each entity keeps whether it's active, and each transform keeps its world matrix until it or something it's inside moves, so a step finds what it works on without walking the scene; a frame of sprites and scripts allocates nothing, and nor does drawing it into the last frame's lists (`BigSceneTests`). A script is called only for the steps its type has (`Update`, `FixedUpdate`, `LateUpdate`), from lists kept until the scene's scripts change, and only the sprites flashing or blinking are moved on each step. A frame is built in one pass over the entities: each is drawn as it's found, in hierarchy order, and then the runs of draws are put back to front by what their entities sort by, each run kept together. Entities in order but for a few stretches (a crowd on one layer with a HUD over it) are merged; others are sorted by key (`StableSort`, a radix sort that skips whatever every entity shares) rather than by comparing them; and the draws move as little as they can (none in a scene already in order; otherwise the biggest block that stays together moves in place and the rest by way of a spare array). An entity knows what kinds of component it has and whether a sprite is all it draws, so the renderer skips the rest without asking each component, and the OpenGL renderer draws each quad as one instance of 80 bytes, in batches of up to 16,384 that each go into fresh buffer storage, so the GPU never waits for the last batch to be read. `FastPathTests` checks each shortcut gives the same game and picture as going through everything. A big scene's work is spread across the cores (`Workers`: the game's thread and up to 15 others take chunks of the work in turn, so a slower core takes fewer, and what comes out is the same however many there are). A frame of a scene of 2,048 entities or more is built in chunks of 1,024, in hierarchy order: each chunk, on whichever thread takes it, draws its plain sprites (an entity at the top of the hierarchy whose sprite is all it draws, with no effects or parallax on it: Griff's own drawing, which reads its entity and writes nothing but its draws, working out where it's drawn without keeping it) into a list of its own and puts them back to front among themselves, which a crowd on one layer already is, so it isn't sorted at all. The game's thread then draws the rest of the entities in hierarchy order (so scripts' drawables are called as they always were), merges the chunks' runs back to front a stretch at a time (as many stretches as chunks for a crowd on one layer with a HUD over it; when they're mixed through each other, as things sorted by Y are, every entry is sorted by key instead), and the chunks copy their draws straight to their places in the last frame's list, overwriting it rather than clearing it first. A crowd of scripts (`[Crowd]`) runs a chunk of 1,024 a thread, each script with numbers of its own from `Rand` (a stream from the crowd's seed and its place in the crowd), and those inside other entities after, on the game's thread. `CoresTests` builds every template's frames (each scene in the editor at two aspects, and the start scene played for 240 uneven frames with random presses, drawn between steps) and mixed crowds of thousands (layers, NaN and -0 Z, sliced, blinking and flashing sprites, children, effects, parallax, things pinned to the screen, sorting by Y, a few things over and under a crowd, many layers) on one thread and in chunks on one thread and on many, and checks they're the same frames, draw for draw and bit for bit; plays two crowds of hopping scripts with random kicks on 1, 5 and 16 threads to the same last bit; checks a crowd runs at its place among the other scripts, that each of its scripts gets numbers of its own, that what a crowd script can't do throws (and changes nothing), that a fault stops the step with the first one in the crowd, and that neither a crowd's step nor a big frame built in chunks allocates. The editor's rewind snapshots (`Timeline`) are the scene file in binary (`SnapshotCodec`: each property read and written through typed delegates, with no text and no boxing, one record an entity, shared with the last snapshot when it hasn't changed), and `TimelineTests` plays every template, rewinds it, and checks each snapshot loads as its scene file would and plays on the same. Physics files shapes in a grid each step (`ShapeGrid`), so a body or a trigger only tests what's near it, in the order it would have met them testing everything. A running game advances once for every frame the screen shows, timed by Windows' compositor (`FramePacer`) rather than WPF's render loop, which on some machines only gets every other one. The editor itself is built from modules: each feature registers its services, commands, panels and menus, and the shell assembles them. Services reach each other through dependency injection (there are no static locators), and a window's or panel's state lives in its view model, which agents reach. The Scene view, for one, is the `SceneView` module: `SceneViewModel` (what it does with the selection, and painting), `SceneViewport` (where it looks) and `TilePalette` are services, and `SceneViewControl` only puts together drawing (`SceneViewDrawing`), where the handles are (`SceneHandleGeometry`) and the mouse and keys (`SceneViewInput`). See `src/Griff.Editor/Themes/README.md` for the design system.

Drawing and networking are open to every component, so the renderer and the network schema know no genre by name. Each component that draws is an `IDrawable` (its draw order, and its step among its entity's draws), changed by its entity's `IDrawEffect`s, and a running game's systems draw what the game itself knows of (`GameSystem.Draw`): a strategy game's fog and HUD, a tactics game's reachable cells, a block world's hotbar, the building tools, and (in `DrawView`, before the rest) a first-person view in place of the top-down one. Each component says what it sends over the network with attributes (`[NetLocal]`, `[PlayerMovement]`, `[Sent]`, `[NotSent]`) or `INetState`, and keeps its entity from players who aren't to see it with `INetSecret` (a card in a face-down deck or another side's hand). `SceneRenderer` keeps only what a view is made of: cameras, parallax, light and dark, and what's pinned to the screen.

Drawing is behind one interface, `IRenderer` (`Griff.Graphics`): a renderer draws a `RenderFrame` into whatever is bound (a window, a framebuffer, a canvas) and can read the pixels back. What a frame becomes is worked out once for every renderer, in `DrawList` (built by `QuadRenderer`, the renderers' base): its quads (80 bytes each, their corners already in clip space, the part of the texture, tint and flash) in draw order, and the passes that draw them (`DrawOp`): runs of one texture's sprites, text a quad a glyph from the glyph atlas's pages, holes, the dark (a light map the size of the screen started at the ambient light, the lights without shadows added up in it together, each light with shadows after its shadows mark a stencil, then multiplied over everything but the HUD), and screen effects (the frame drawn into a picture, then onto the screen through them), with the colors and settings they take worked out and clamped there too. `QuadRenderer` also numbers the images a frame draws and loads each once (again when its file changes), and hands over the rows of glyph pages text added glyphs to before the frame is drawn. A renderer for a graphics API only runs the passes: `OpenGLRenderer` (`Griff.Graphics.OpenGL`) on the desktop, and `WebGLRenderer` in the browser, which hands the page the draw list in one call a frame for `griff.js` to run the same way with WebGL 2. The shaders are written once (`Shaders`, GLSL with a header for each: OpenGL 3.3, or GLSL ES 3.00 for WebGL), and both run them at full precision, so they draw the same pixels: `tools\web.ps1 -Compare` draws every template's start scene, and scenes of lights, shadows, screen effects and a viewport, both ways and compares the pictures. The passes name no API's state, so Direct3D 11 is one more class that runs them (with the shaders in HLSL), and textures drawn into are flipped by each renderer as its API needs. A camera drawn into part of the screen is a view: a `View` pass clips drawing to its part (clip space stays the whole screen, so its frame is projected there), then its background and its frame's passes, lit by itself if it's dark (`RenderFrame.Views`, drawn by `DrawList.AddView`). `DrawListTests` pins the passes (and that `griff.js` has no shader of its own and numbers the passes as `DrawOp` does), and a frame of text that changes and shadows makes no garbage.


A genre is a module: everything of it in one folder under `src/Griff/Modules` with a namespace to match (`Griff.Modules.Match3`), its components, its system (which runs it, keeps what it tracks and draws what no one entity does), its network commands, its template with its pictures, and the Entity menu's presets for it (`EntityPreset`) and things it does to the selection (`EntityAction`, such as Generate Dungeon), which the editor makes into commands and agents' tools. Every genre is a module: Battles, Block Worlds, Cards, Contraptions, Dungeons, Falling Blocks, First Person, Match-3, Puzzles (goals and undo for grid puzzles), Strategy and Tactics. A module registers once, in its `GameModule` class's `AddTo`: its systems, and each of their steps next to the step of the frame it follows or goes before (`StepAfter("Dragging", "Match Boards", ...)`), so the frame keeps its order; the commands players' machines send its host (`OnNetCommand`), and those the host sends one player's machine (`OnHostCommand`). Everything else of it is found. The core names no module, and no module names another, so each stands alone: Griff's own components reach a module's through interfaces they call (a Counter counts from an `ICounterSource`, grid movement asks an `IGridDriver` for its steps, turns tell `ITurnReady` components a turn has begun, `Game.Send` tells `IHearsMessages` components, building tools leave the number keys to an `IClaimsNumberKeys` component, `IPlaytestReport` adds to what an agent playing the game is told, and a module's component lists itself on a core component's Works With, `[WorksWith(..., Back = ...)]`), and the game asks its systems (`GameSystem.MouseOnHud`, `ClaimsBack`, `PlayersChanged`, `DrawView` and `Eyes`, `LayOutHud`, `HudButtons` and `Notice`, `RunForPlayer`, `GridStepStarting`, `SceneEnding`). Turns, grid movement, switches, inventories and trails stay in the core: Griff's own components build on them (grid movers step a turn at a time, attacks use a turn's actions, a door takes a key, a dash leaves a trail) and so do several genres, so each is a foundation with its own extension points rather than a genre. A script component or system can use every one of them. What a module offers scripts as part of `Game` is in extension members (`Game.Train`, `Game.Selected`, from `StrategyGame`), and scripts get every module's namespace without a `using`; components keep the names they're saved under (`[ComponentName("Griff.MatchBoard")]`), so scenes made before the move load as they were.

Components and templates are found rather than listed. Every component in `Griff` is registered without being named anywhere (`ComponentRegistry.CreateDefault`, which scripts' components join the same way on each compile), and every `ProjectTemplate` (a class with its description, its place in New Project's list and what it builds: scenes, prefabs, scripts, pictures and music) is offered by New Project and played by the template tests (`ProjectTemplates.All`). Adding either is adding a class. Scene data outlasts changes to them: a component can say what it was called before (`[FormerName]`), version its data with upgrade steps (`[ComponentVersion]`, `[UpgradeFrom]`), and keeps values it has no property for. `ComponentSwap` is what hot reload uses to rebuild script components in place when their types change.

Tests keep the architecture in shape, so a change that breaks it fails rather than slipping in:
- **Layers:** nothing in `Griff.Scenes` (data) uses `Griff.Runtime` or `Griff.Rendering` (`LayerTests`).
- **Extension points:** the renderer, the frame systems draw into and the network schema name no component but those a view or an entity's networking is made of (`ExtensionPointTests`).
- **Genre modules:** the core (everything in `Griff` outside `Modules`) names no module's types, no module names another's, each module keeps to its own folder and namespace with one module class, and a module's components are data like the core's, using neither `Griff.Runtime`, `Griff.Rendering` nor its systems (`ModuleTests`, `LayerTests`).
- **Agents:** every command is an MCP tool with a description, every panel and service is reachable (`AgentSurfaceTests`), and no code-behind (`*.xaml.cs`) runs an edit or starts a process, where agents couldn't reach it (`CodeBehindTests`).
- **Editor modules:** the shell registers none of a feature's types (each module registers its own), and no editor service sets a static of itself for others to reach it by (`SceneViewStructureTests`).
- **Players:** a template is exported with both players and run for real; it has to draw a frame (`PlayerSmokeTests`).
- **Renderers:** a frame is worked out once for every renderer (`DrawList`), the browser's page has no shader of its own and numbers the passes as `DrawOp` does (`DrawListTests`), and the OpenGL renderer draws sprites, the dark and screen effects with no garbage (`OpenGLRendererTests`); `tools\web.ps1 -Compare` checks the browser draws the same pixels.


Neither the layer test nor the code-behind test has exceptions left.
